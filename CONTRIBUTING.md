# Участие в разработке

## Текущие владельцы работ

В команде четыре активных участника: Product/Business Analyst совмещает работу над промптами и оценкой качества; отдельно работают Frontend, Backend и ML Engineer. Пятый участник сейчас в отъезде, сроки его возвращения неизвестны, поэтому его не назначают единственным владельцем блокирующей задачи.

## Изменения

- Берите небольшой ID задачи из `docs/backlog.md`, проверьте зависимости и согласуйте контракт до параллельной работы.
- Для параллельной работы назначайте одного автора изменений на каждый файл. Делегируйте узкие самостоятельные части; перед объединением запрашивайте ревью у владельца соседнего слоя.
- Ветку называйте `codex/<task>` с коротким смысловым идентификатором задачи.
- Коммит оформляйте по Conventional Commits: русский формат `<type>: <краткое описание>`, например `docs: уточнить сценарий демонстрации` или `fix: проверить происхождение вывода`. Описание коммита — на русском.
- Не кладите ключи, локальные `.env`, реальные клиентские данные и банковские документы без подтверждённого разрешения в репозиторий.

## Проверка перед интеграцией

Используйте проверки из корневого README и README конкретного модуля. В описании изменения укажите выполненную команду и результат; если проверка не запускалась или требует внешнего доступа, так и напишите. Не делайте вывод о готовности кейса только по успешной сборке или тестам.
