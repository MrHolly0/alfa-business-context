# Участие в разработке

## Зоны работы

- Аналитика бизнеса и промпты: сценарии, контекст компаний, источники и критерии качества.
- Frontend: `apps/web`, пользовательский сценарий и отображение результата.
- Backend: `apps/core`, Symfony/PHP, права, бизнес-данные, задания и публикация.
- Анализ данных: `apps/intelligence`, сбор, поиск, модели, конфигурации и оценка.

Форматы между частями описаны в [контрактах](contracts/intelligence/README.md). До изменения схемы согласуйте её с потребителями. Для параллельной работы назначайте одного ответственного за файл, затем проверяйте изменения у владельца смежного компонента.

## Ветки и коммиты

Основная ветка — `main`. Ветку создавайте под одну задачу: `feat/company-profile`, `fix/source-filter` или `docs/setup`. После включения изменений в `main` удаляйте завершённую ветку.

Коммиты: `type: описание на русском`, до 72 символов, например `fix: учитывать исключённые источники`. Сохраняйте своё обычное авторство, без дополнительного соавторства. Сообщение описывает изменение кода или документации.

## Документация входит в задачу

При изменении поведения обновляйте соответствующий документ в том же наборе изменений:

| Изменение | Что обновить |
|---|---|
| Возможности или структура проекта | Корневой README и `docs/architecture.md` |
| Команды и настройки | README компонента, `docs/development.md`, при необходимости `infra/README.md` |
| API, входы и результаты | Схемы, примеры и описание в `contracts` |
| Аналитика и модели | Документ модуля, `docs/ai-process.md`, матрицу готовности |
| Оставшиеся задачи | `docs/backlog.md` |

Перед завершением проверьте команды, ссылки и соответствие описания коду. Архивные материалы отмечайте как исторические и связывайте с действующей инструкцией. Не называйте план реализованной функцией и не выводите качество анализа из успешного теста схемы.

## Проверка изменений

Используйте команды из [инструкции разработки](docs/development.md) и README затронутого компонента. Укажите выполненные проверки и результат. Для Python-контрактов выполните `scripts/export_contracts.py --check`; после согласованного изменения моделей обновите экспорт и примеры.

Ключи, `.env`, локальные состояния и клиентские данные в Git не включайте. Модельные проверки запускайте отдельно, с разрешёнными данными и бюджетом; обычные тесты не требуют ключей.
