# Корпус документов

`intelligence.corpus.CorpusStore(path)` хранит документы, неизменяемые ревизии и фрагменты evidence в PostgreSQL. `path` — стабильный логический ID хранилища (в старых примерах он может иметь суффикс `.sqlite3`), а не SQLite-файл. Однократный importer читает legacy SQLite источник только в режиме чтения; новые поля применяются миграциями PostgreSQL. `ingest(document)` принимает контракт `DocumentInput`, сохраняет `tenant_id`, `source_id`, роль источника, canonical URI и даты; URL остаётся метаданными и никогда не загружается. `fetched_at` задаёт вызывающая сторона; хранилище сохраняет это значение для первого наблюдения и обеспечивает строго возрастающее время доступности версий документа, но не подтверждает фактическое время получения. Изменение текста или значимых метаданных (заголовок, дата публикации, издатель, язык, тип содержимого) создаёт ревизию; метаданные издателя и языка хранятся в каждой версии.

Парсер поддерживает `text/plain`, `text/html`, RSS/XML через `defusedxml` и PDF через `pypdf`. Размер обычного текста и RSS ограничен 2 млн символов. PDF ограничен 20 МБ декодированных данных, соответствующим пределом base64 и 100 страницами; ошибки размера отделены от ошибок формата. Парсер сообщает о PDF без извлекаемого текста как о вероятно сканированном. RSS ограничен 500 материалами; записи из RSS сохраняются отдельными документами с собственной датой публикации и стабильной ссылкой (RSS text-link, Atom canonical/alternate href, затем guid/id).

## Закрытый набор организаторов: PDF и локальный OCR

Обычный API-ingest остаётся ограничен PDF до 20 МБ. Для приватного локального набора есть отдельный доверенный путь `case-import`: он читает оригинал только из заданной локальной папки, проверяет SHA-256 и тип файла, ограничивает PDF 50 МБ и OCR 100 страницами на файл. Это не добавляет крупные PDF в публичный HTTP API.

Сканы распознаются локально `pdftoppm` и Tesseract `rus+eng`; в тексте сохраняются маркеры страниц, а оригинальные байты PDF и исходный SHA-256 остаются provenance материала. OCR не заменяет оригинал и может ошибаться: цитаты из него нужно сверять с соответствующей страницей PDF. Для поиска требуются дата публикации и остальные обязательные метаданные; дата из имени файла или Drive не подставляется.

В наборе организаторов проверены девять PDF и распознаны 64 страницы. Восемь материалов получили дату и были импортированы для трёх выбранных компаний (24 готовые bank-документные копии); девятый, обзор золота, остаётся `pending_metadata`, пока не подтверждён точный день публикации. Подготовка профилей и документов не вызывает модель. Повторный `case-import` с теми же оригиналами и OCR возвращает прежние revision refs; проверенный повтор оставил все 24 документа на ревизии 1.

Из контейнера с собранным сервисом команду можно выполнить так (case-папка не входит в image):

```sh
docker compose -f compose.yaml -f compose.judging.yaml --profile tools run --rm --no-deps \
  -v "$(pwd)/.local/data/case:/case:rw" intelligence case-import \
  --manifest /case/manifest.json --state-dir /app/.state --output case-bundle.json
```

Команда печатает только счётчики; bundle содержит приватные профили и provenance и должен оставаться вне Git с правами владельца. Подробный сценарий Core/Web находится в [инструкции проверки кейса](../../../docs/judging.md).

`search(...)` выполняет лексический поиск для русского и английского текста. Tenant, список разрешённых source IDs, роль, `as_of` и явные revision refs ограничивают кандидатов до ранжирования. Без указания ревизии доступна только последняя версия документа на выбранное время. Повторные материалы с одинаковым содержимым занимают одно место в выдаче. Цитаты имеют стабильные ID, hash и локатор смещения или страницы, длина цитаты не превышает 1000 символов. `get_evidence(...)` повторно проверяет tenant/source/time scope.

Проверки offline из каталога `apps/intelligence`: `.venv/bin/python -m pytest -q -p no:cacheprovider tests/test_corpus.py tests/test_parsers.py`.
