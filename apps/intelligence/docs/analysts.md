# Настройки аналитика

`AnalystConfig` задаёт безопасные предпочтения поверх шаблона `analysis-v2`: фокус, порядок поиска, стиль ответа, горизонт, лимит свидетельств, короткие поисковые термины и примеры из закрытых перечислений. Свободный системный prompt не принимается; настройки передаются как данные и не меняют проверки JSON, происхождения свидетельств или границ инструментов.

`PromptRegistry(path)` хранит версии конфигураций и журнал активаций в SQLite. Встроены `baseline@1`, `finance@1`, `procurement@1` и `executive@1`; по умолчанию применяется baseline. Чтобы зарегистрировать свою конфигурацию, вызовите `register(config)`. Pipeline принимает `analyst_config=` для явного выбора либо `registry=` для выбора активированной настройки по роли и отрасли. Порядок выбора: точные роль и отрасль, wildcard отрасли для роли, точная отрасль для любой роли, затем wildcard для любой роли. Неактивированные варианты сами по себе не участвуют в выборе.

Продвижение `promote(...)` требует отчёт `tournament-report-v1`, совпадения победителя и ref, пригодности к продвижению, реального (не синтетического) holdout, успешной проверки holdout и одобрения тем же reviewer. Каждая активация добавляет ревизию и digest отчёта; `expected_revision` защищает от конкурентной записи. `rollback(...)` добавляет новую ревизию с предыдущей конфигурацией. Результат анализа записывает фактический ref в `versions.analyst_config`.

Локальная проверка из `apps/intelligence`: `.venv/bin/python -m pytest -q -p no:cacheprovider tests/test_analysts.py tests/test_pipeline.py tests/test_schemas.py`.

Турнир для публикации фиксирует `PromptRegistry.snapshot(scope)`: активный ref, ревизию области и источник fallback. `promote` сверяет снимок в той же транзакции, что записывает активацию, и требует свежий holdout. Отчёты старого формата без сравнения с активной версией публиковать нельзя; они остаются доступными для просмотра.

## Персональная настройка компании

`CompanyAnalystStore(path, registry)` хранит отдельные версии по паре tenant/company, не помещая их в общий `PromptRegistry`. Вызов `onboard(tenant_id, company_id, context_version, company, llm=None)` выбирает активный шаблон или, при явно переданном `LLMService`, просит модель подобрать только ограниченные предпочтения. Без LLM работает детерминированный fallback. В настройке остаются только закрытые поля: до шести коротких поисковых терминов, до трёх примеров из закрытых перечислений и `max_depth` от 2 до 3. Сырые факты, описания, имена, источники, права и команды в конфиг не сохраняются.

`get(tenant_id, company_id)` возвращает текущую версию; `mark_stable(...)` помечает выбранную стабильную версию; `rollback(..., expected_revision=...)` создаёт новую ревизию из предыдущей стабильной. У каждого tenant/company своё пространство имён и история.
