# Настройки аналитика

`AnalystConfig` задаёт безопасные предпочтения поверх шаблона `analysis-v2`: фокус, порядок поиска, стиль ответа, горизонт, лимит свидетельств, короткие поисковые термины и примеры из закрытых перечислений. Свободный системный prompt не принимается; настройки передаются как данные и не меняют проверки JSON, происхождения свидетельств или границ инструментов.

`PromptRegistry(path)` хранит версии конфигураций и журнал активаций в SQLite. Встроены `baseline@1`, `finance@1`, `procurement@1` и `executive@1`; по умолчанию применяется baseline. Чтобы зарегистрировать свою конфигурацию, вызовите `register(config)`. Pipeline принимает `analyst_config=` для явного выбора либо `registry=` для выбора активированной настройки по роли и отрасли. Порядок выбора: точные роль и отрасль, wildcard отрасли для роли, точная отрасль для любой роли, затем wildcard для любой роли. Неактивированные варианты сами по себе не участвуют в выборе.

Продвижение `promote(...)` требует отчёт `tournament-report-v1`, совпадения победителя и ref, пригодности к продвижению, реального (не синтетического) holdout, успешной проверки holdout и одобрения тем же reviewer. Каждая активация добавляет ревизию и digest отчёта; `expected_revision` защищает от конкурентной записи. `rollback(...)` добавляет новую ревизию с предыдущей конфигурацией. Результат анализа записывает фактический ref в `versions.analyst_config`.

Локальная проверка из `apps/intelligence`: `.venv/bin/python -m pytest -q -p no:cacheprovider tests/test_analysts.py tests/test_pipeline.py tests/test_schemas.py`.

Турнир для публикации фиксирует `PromptRegistry.snapshot(scope)`: активный ref, ревизию области и источник fallback. `promote` сверяет снимок в той же транзакции, что записывает активацию, и требует свежий holdout. Отчёты старого формата без сравнения с активной версией публиковать нельзя; они остаются доступными для просмотра.

## Персональная настройка компании


Новая компания получает приватную baseline-конфигурацию синхронно, без вызова модели. Повторный `onboard` той же версии контекста идемпотентен. При новой версии контекста сохраняется выбранная стратегия в новой неизменяемой ревизии; устаревшая версия возвращает `stale_context`, а повторное использование номера версии с другим содержимым отклоняется.

Оптимизация — отдельный ограниченный вызов `CompanyAnalystStore.optimize(tenant_id, company_id, context_version, company, llm, expected_revision=...)`. Ревизию нужно захватить при постановке задачи. Генерация выполняется вне транзакции; публикация требует совпадения версии контекста и ожидаемой ревизии. Конкурентное обновление возвращает `revision_conflict`, устаревший снимок — `stale_context`; ошибка генерации оставляет текущую конфигурацию и возвращает `optimization_failed`. Обычный onboarding не запускает генератор.

Конфигурация хранит только закрытые предпочтения анализа и ограниченные поисковые термины. Сырые сведения компании, названия, описания, утверждения и provenance не передаются генератору и не сохраняются в настройке. Учет направления деятельности не ограничивается первым совпадением; неизвестное значение остаётся `unknown`, не `services`.

```python
record = store.onboard(tenant_id, company_id, context_version, company)
record = store.optimize(tenant_id, company_id, context_version, company, llm,
                        expected_revision=record["revision"])
record = store.rollback(tenant_id, company_id,
                        expected_revision=record["revision"])
```

`rollback` создаёт новую ревизию с предпочтениями предыдущей отмеченной стабильной версии, сохраняя текущий снимок профиля и его версию. Историю не переписывает. Если одновременно изменились активная конфигурация реестра и профиль, onboarding применяет новую конфигурацию реестра. Публикация общей версии через `PromptRegistry.promote` требует актуального snapshot области, свежего holdout, пройденной отдельной проверки и подтверждения человека. Конфигурация аналитика является стратегией общего механизма, а не отдельной обученной моделью.
