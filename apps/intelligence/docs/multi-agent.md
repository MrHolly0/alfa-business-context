# Многошаговый персональный анализ

`MultiAgentPipeline` добавляет к существующему анализу логические этапы исследования, анализа и критики. Исследователь возвращает до четырёх коротких поисковых запросов только для ролей `external` и `bank`. Приложение выполняет их через `CorpusStore`; модель не получает URL, SQL, shell или сеть. Результаты проходят прежние проверки tenant, разрешённых источников, `as_of`, ревизий, хешей цитат и первичного события. Если свидетельств или актуального контекста недостаточно, основной pipeline делает один ограниченный расширенный поиск и повторяет проверки.

Аналитик использует существующие `AnalystConfig`, промпт и строгие grounding-проверки. Кандидат сохраняет неизвестность, альтернативы и условия опровержения; гипотезы должны содержать проверяемое условие подтверждения и горизонт либо уточняющий вопрос. Прямые связи допустимы: несколько переходов не конструируются без оснований. Критик получает исходное событие и evidence кандидата, проверяет противоречия и недостающие звенья. Полный профиль передаётся только в явно синтетическом исполнении с синтетическими основаниями. В остальных случаях профиль и общий пакет критику не передаются, поэтому проверка персональной применимости ограничена. Замечания критика проходят проверку ID и evidence refs, могут понизить `ready` до `partial`, но не отменяют программные проверки и не доказывают истинность.

Если критик возвращает `review`, подтверждённые ссылки на проблему и до двух поисковых фраз, приложение запускает ровно один повторный анализ через тот же `AnalysisPipeline`. Фразы остаются запросами к разрешённому корпусу и проходят прежние ограничения источников, ревизий и времени. Повтор должен выбрать хотя бы одно новое свидетельство, иначе первоначальный кандидат остаётся `partial`. Даже при новых основаниях результат остаётся `partial` до повторной семантической критики; система не объявляет противоречие снятым.

Все роли используют существующий `LLMService` и общий лимит вызовов, токенов и шагов. `max_steps` ограничивает поиск, проверки и анализ внутри `AnalysisPipeline`; checkpoint остаются точками отмены. Для сервисов проверяются одинаковые account scope, валюта и SQLite ledger. При нехватке бюджета этапы пропускаются с записью в trace; скрытых повторов нет. `max_model_calls: 3` хватает только на три вызова, например аналитика, критика и один проход адаптации, если исследователь уже использовал детерминированный план. В полном `DataWorkflow` общий пакет обычно заменяет модельный вызов исследователя, но извлечение общего пакета тоже расходует бюджет. Значение по умолчанию `2` сохранено для совместимости. Если адаптация или повторная проверка не помещается в оставшийся бюджет, вывод остаётся `partial`.

Задание можно прервать через существующий `checkpoint(stage)` callback. Worker передаёт сюда проверку актуальности lease; ошибка callback прерывает текущую операцию и передаётся worker без преобразования в успешный результат. Отдельное сохранение и восстановление промежуточных стадий не входит в текущий контракт.

## Вызов

```python
pipeline = MultiAgentPipeline(
    store,
    llm=default_llm,
    analyst_config=analyst_config,
    registry=prompt_registry,
    role_services={"researcher": researcher_llm, "analyst": analyst_llm, "critic": critic_llm},
)
candidate = pipeline.run(request, checkpoint=lease_check)
```

`role_services` необязателен; неуказанные роли используют `llm`. Роли могут оставаться логическими: без отдельного исследователя применяется bounded deterministic query plan. В результате `usage.workflow`, `usage.attempts`, `usage.reserved_tokens`, `usage.critic_review`, `trace` и `coverage.limitations` показывают фактически выполненные этапы и ограничения.

Опциональный `shared_event_package` проверяется по tenant, event/revision и разрешённым source IDs; в результате сохраняется только `shared_package_ref`. Минимальная проекция пакета может попасть в аналитика только при явном public/synthetic исполнении и соответствующей сохранённой классификации каждого источника. Она не становится свидетельством автоматически и не заменяет возврат к оригиналу.

Проверка из `apps/intelligence`: `.venv/bin/python -m pytest -q -p no:cacheprovider tests/test_multi_agent.py tests/test_pipeline.py`. Тесты используют SQLite fixtures и подставленные роли; живые провайдеры не вызываются. Сбор и event package описаны отдельно; их наличие не означает, что внешний источник доступен или разрешён.

В полном `DataWorkflow` исследователь использует локальный ограниченный план: общий пакет уже содержит термины события. Извлечение общего пакета, анализ, один repair, критика и возможная адаптация делят один бюджет задания. Если отвергнутый длинный ответ не помещается во входной лимит repair, код использует краткие диагностические коды, а не повышает ограничения.
