# Профиль компании и персональный анализ

Эта страница описывает текущие Python-функции подготовки профиля и сравнения персональных результатов. Это рабочая логика и синтетическая проверка, а не подключённый пользовательский путь через PHP Core.

## Описание → предложение профиля

`prepare_description` преобразует текст в ограниченное предложение на основе `company-context-v2`. Поддерживаются явные фразы о направлениях, поля `направления:`, `зависит от:` и `факты:`. Неизвестная свободная проза сохраняется в `description`; система не угадывает деятельность по отрасли. Каждая выделенная запись связана с цитатой и смещениями в исходном тексте. Для новых фактов и направлений ставится `observed_at` из `as_of`, без выдуманной даты действия.

Без модели разбор детерминированный. Через CLI:

```sh
cd apps/intelligence
.venv/bin/python -m intelligence prepare-description \
  --input examples/description-context.json \
  --output /tmp/description-proposal.json
```

Запрос соответствует [`DescriptionPrepareRequest`](../contracts/intelligence/description-prepare.schema.json): tenant/company, имя, описание, происхождение, `as_of`, классификация данных и, если Core уже проверил анкету пользователя, `statement_status: "core_confirmed"`. CLI и синхронный внутренний маршрут `POST /internal/v1/company-context/from-description` возвращают только детерминированное предложение и не обновляют канонический профиль. Если передать тот же запрос как DataTask `operation=prepare_description`, предложение входит в обычный workflow result и сохраняется в его кэше результатов; это не сохранение профиля.

Файл `examples/description-context.json` — готовый синтетический вход для этой CLI-команды, а не полный pipeline. Полное сравнение «описание → proposal → Core acceptance → analyst config → personal result» находится в [отчёте сравнения](checks/personalization-comparison-2026-10-25.json); его входы — [personalization-comparison.json](../apps/intelligence/examples/personalization-comparison.json).

Для общего `DataTask` доступна операция `prepare_description`. Настроенная модель/маршрут `generator` может опционально разбирать разрешённые `public`/`synthetic` данные через LLM. Каждое извлечённое утверждение должно совпадать с точной цитатой. Если quote встречается ровно один раз, Python может сам исправить ошибочные модельные offsets; неоднозначная или отсутствующая цитата отвергается. Модельное предположение остаётся предположением. Конфиденциальный текст не отправляется внешнему провайдеру. Core должен принять предложение и сохранить собственную версию профиля.

Дословное пользовательское утверждение после подтверждения Core может стать записью со статусом `confirmed`; это подтверждает источник анкеты, а не независимую проверку. Неотвеченные поля, отрицания и модальные слова не превращаются в подтверждённые зависимости или действующие направления. Для каждой гипотезы создаётся отдельный уточняющий вопрос. Система не выводит финансовые показатели из описания.

## Baseline и оптимизация настроек

Операция `onboard` сразу создаёт рабочую базовую настройку аналитика и её версию на основе профиля, переданного Core. Обычный анализ может пользоваться этой настройкой без ожидания генерации. Python хранит версию конфигурации и fingerprint, но не становится владельцем канонического профиля. В настройку входят ограниченные предпочтения аналитика; она не является причинным вердиктом о воздействии события.

После успешного `onboard`, либо когда настройка пересобрана после изменения контекста, Python возвращает в `DataResult.follow_up_intents` ограниченный `ai-follow-up-intent-v1`. При включённом `auto_optimize` такой intent может также появиться после `analyze`, `collect` или `reassess`, если для компании создана подходящая базовая конфигурация. В intent передаются tenant/company, версия контекста, fingerprint профиля, ожидаемая версия настройки, причина и идемпотентный ключ.

Дальше Core:

1. проверяет intent, актуальный профиль и ожидаемую ревизию;
2. принимает уже сохранённый результат родительской задачи;
3. применяет собственную `AutoOptimizationPolicy` с отдельным конечным лимитом задач, модельных вызовов, токенов, шагов и резервом в RUB или USD;
4. если бюджет и лимиты разрешают, создаёт обычный `ai-job-v1` с `operation=optimize` и ожидаемой ревизией настройки.

`AutoOptimizationPolicy` — отдельное распределение Core, не бюджет родительского анализа. Если политика отсутствует или исчерпан её лимит, intent получает `skipped_budget`; автоматическая генерация не происходит. Результат оптимизации не подменяет уже выполненный анализ. Пример конечного распределения: [`auto-optimization-policy.json`](../apps/intelligence/examples/auto-optimization-policy.json), один job с резервом $0.01. Он включается только операторским флагом стенда `--auto-optimization-policy`, а не пользовательским intent. PHP hook на событие сохранения компании и автоматическая постановка из настоящего пользовательского приложения пока не подключены; это поведение проверяется контрактным fixture stand.

## Сравнение на одинаковых событиях

Воспроизводимый локальный сценарий:

```sh
docker compose run --build --rm intelligence demo-personalization
```

Сценарий `examples/personalization-comparison.json` содержит две учебные компании одной отрасли с разными зависимостями и третью смешанную компанию. Один и тот же синтетический набор событий проходит через реальный локальный сбор, лексический отбор, поиск по корпусу и baseline-анализ. Транспорт RSS подменён локальной фикстурой; сетевой запрос и модель по умолчанию не используются. Команда выводит JSON в терминал. На хосте из `apps/intelligence` можно сохранить его через `uv run --frozen python -m intelligence demo-personalization --output /tmp/personalization-comparison.json`. Файл результата включает предложения профилей, конфигурации, выполненные запросы поиска, кандидаты и сигналы отбора. Текущий проверенный срез: [отчёт сравнения](checks/personalization-comparison-2026-10-25.json).

Примеры приоритета в отчёте:

- событие о Северном порте даёт сигнал `0.8` двум компаниям с этой подтверждённой зависимостью;
- событие о Восточной электроподстанции даёт сигнал `0.8` компании, зависящей от её работы;
- событие OrionCloud даёт сигнал `0.8` смешанной компании, где облачная зависимость указана отдельно от производства и импорта.

Каждый сигнал `0.8` — детерминированный лексический приоритет по совпадению зависимости и термина события, а не вероятность воздействия и не измеренная тяжесть. Нулевой сигнал означает отсутствие совпадения в переданном профиле и snapshot, но не доказывает отсутствия риска. В коде нет веток для названий компаний или заранее заданных отраслей. Использованные запросы и основания поиска сохраняются в отчёте.

Персональный результат baseline не делает причинного вывода: он показывает подтверждённые сведения профиля, подходящие к событию, неизвестные условия и уточняющий вопрос. Например, совпадение зависимости не подтверждает убыток, запас, долю выручки или срок восстановления. В демонстрации кандидаты ожидаемо остаются `partial`.

## Статусы и что показывать человеку

У результата задачи и у кандидата разные статусы.

| Уровень | Статус | Отображение |
|---|---|---|
| `DataResult` | `completed` | Задача выполнена; проверить статусы отдельных кандидатов и конфигураций. |
| `DataResult` | `partial` | Есть частичные результаты либо ограничение/ошибка настройки; показать причины из coverage, кандидата и конфигурации. |
| `DataResult` | `no_change` | Core передал точный proof уже опубликованной оценки с тем же входом; повторно не создавать публикацию. |
| `DataResult` | `unknown` | Кандидат не получен; это не подтверждает отсутствие воздействия. |
| `CandidateAssessment` | `ready` | Достаточно оснований для полного кандидата по текущим правилам; это всё ещё решение Core о публикации. |
| `CandidateAssessment` | `partial` | Вывод ограничен: например, нет подтверждённой связи, банковской позиции, применимых материалов или нужного уточнения. |
| `CandidateAssessment` | `unknown` | Проверяемый кандидат не собран или нет пригодных evidence. |

Для `partial` интерфейс должен показывать `coverage.limitations`, `clarifications`, `claims`, evidence и trace рядом со статусом. Типичные причины: отсутствует банковская позиция; нет подтверждённой зависимости; нужные документы недоступны по snapshot; контекст не датирован; модельный ответ отклонён либо недоступен; не подтверждены условия применимости. Не переводить частичный результат в чистый положительный/отрицательный вердикт.

Core принимает `ai-result-v1`, проверяет lease, `context_version`, `source_policy_version`, конфигурацию и подпись входа, а затем самостоятельно решает, создавать ли новую публикацию. Для повтора автоматизации Core использует `follow_up_intents` только после приёма родительского результата и повторной проверки актуальности/идемпотентности.

## Модели и качество

Механизм турнира действительно реализован отдельно от обычного анализа: сравнение конфигураций, программные gates, blind review, holdout/shadow и ручное продвижение. Но fixture judge, синтетические cases и тесты подтверждают механику, не качество персонального анализа на реальных банковских данных. Независимая оценка на размеченном наборе не проведена.

OpenRouter использовался в отдельных живых проверках; попытка и её стоимость приведены в [отчёте live-персонализации](checks/personalization-live-2026-10-25.json), сводные прогоны — в [отчёте live-проверок](ai-live-checks.md). Первый live-разбор описания использовал детерминированный fallback; после исправления подсчёта смещений единственной точной цитаты повтор завершился в режиме `llm`. Все предложения требуют проверки Core. Девять модельных кандидатов остались `partial`. Расходы обеих попыток и пределы проверки приведены в [актуальном отчёте](ai-personalization-checks.md). Для шлюза Альфы есть настроенные метаданные и адаптер, но доступность генерации и тарифы для реального аккаунта не подтверждены. Неизвестный тариф не означает, что модельный шлюз технически не умеет генерировать; текущая безопасная конфигурация не отправляет запрос без известных ставок и резерва. Неизвестная стоимость не равна нулю. Не включайте модельный режим для получения персонального профиля без разрешённой классификации и бюджета.
