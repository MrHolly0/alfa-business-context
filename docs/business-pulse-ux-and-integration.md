# Бизнес-пульс: UX и интеграция метрик

Дата: 26 октября 2026. Статус: локальный интерактивный прототип. ML и backend ниже — план реализации, не подключённые возможности.

## Что изменено в интерфейсе

Один сервис «Бизнес-пульс» в банковском меню по референсу. /#home — основной дашборд, /#overview сохраняется как совместимый вход. Существующие ситуации, новости, исследования, профиль, источники, история, обратная связь и помощник доступны внутри сервиса. Остальные пункты банковского меню выключены. Баланс и шесть значений показателей заданы демонстрационными константами.

В начале — общая картина с быстрым выбором 7/30/90 дней и своего диапазона. Окно данных отсчитывается от последней доступной публикации, дата явно показана. Фильтр меняет подборку событий и первый связанный вывод. Это воспроизводимый обзор по правилам; свободная генерация общего мнения не подключена. Значения карточек пока за последний отчётный месяц, не пересчитываются при смене периода.

Метрика открывает тематическую подборку материалов. Сохраняются прежний контекстный помощник, обсуждение источника и фидбек из разбора ситуации. Первый вход запускает единый обязательный тур по всем основным разделам; повторный вызов — «?» в шапке. Прогресс и завершение хранятся локально. Пользовательская метрика сохраняется отдельно по компаниям; в демо пользователь сам выбирает тему, по которой отбираются материалы. Описание пока не отправляется модели.

## Универсальные показатели

| Показатель | Определение | Данные | Каналы новостного влияния |
|---|---|---|---|
| Выручка | Доход от продаж за период | ERP, управленческий учёт | Спрос, клиенты, рынки |
| Операционная маржа | Операционная прибыль / выручка | Управленческая отчётность | Сырьё, энергия, зарплаты, цены |
| Денежный поток | Поступления минус выплаты | Казначейство, счета | Платёжные условия, ставки, задержки |
| Долговая нагрузка | Чистый долг / EBITDA | Долговой реестр, отчётность | Ставки, рефинансирование |
| Срок оплаты клиентами | Согласованная формула DSO | Дебиторская задолженность | Состояние покупателей, расчёты |
| Операционные расходы | Расходы на ведение деятельности за период | Управленческий учёт | Персонал, аренда, услуги, технологии, закупки |

Это стартовый набор для нефинансовых компаний. Отраслевые показатели пользователь добавляет отдельно. Для корпораций нужны разрезы по группе, дочерней компании, направлению, региону и валюте. Состав и определения утверждает бизнес. При отсутствии данных показывать «Нет данных», не ноль. Для нулевой/отрицательной EBITDA коэффициент долговой нагрузки требует отдельного состояния, а не деления по умолчанию.

## Пользовательские метрики

Пользователь задаёт название, описание, единицу, направление хорошего изменения, период, границы компании/направления и источник фактических значений. Дополнительно: формула, целевой диапазон, порог значимого изменения, связанные продукты, клиенты, страны, поставщики и горизонт влияния.

Пример: «Стоимость доставки партии, ₽/партия: перевозки из Китая в Москву; важны топливо, железнодорожные тарифы и сроки таможни». ИИ предлагает связанные сущности, источники и поисковые запросы, объясняет связь и задаёт уточнение при неоднозначности. Пользователь подтверждает интерпретацию. Система затем отслеживает разрешённые источники под этот показатель. Фактическое значение поступает из учёта или ручного ввода; модель не выдумывает числа из новостей.

## Работа для ML

1. Добавить версионируемый MetricDefinition в снимок задания: metric_id/version, company_scope, description, formula/unit, direction, horizon, target/thresholds, entity_refs, approved_source_scope. Определение пользователя трактуется как данные, не инструкция модели.
2. Реализовать prepare-metric: нормализованное определение, вопросы, предполагаемые связи и запросы. Возвращать предложение для подтверждения в Core. Не менять права, источники или лимиты из текста метрики.
3. Включить подтверждённые метрики в подбор источников и ранжирование. Сначала применять доступ и актуальность, затем relevance. Различать простое совпадение темы и обоснованный канал влияния.
4. Возвращать MetricImpact: metric_id/version, event_id/version, relevance, direction (up/down/mixed/unknown), horizon, evidence_refs с фрагментами, механизм влияния, альтернативы, неизвестные и follow_up. Не выдавать эвристический балл за вероятность.
5. Общий обзор периода: период, as_of, доступное покрытие, главные изменения, источники, неизвестное и следующий шаг. Общая картина использует последнее согласованное состояние; выбор дат использует явно выбранный режим retrospective/as_known. Фактические изменения метрик считаются кодом по рядам наблюдений.
6. Пересмотр при изменении определения, контекста, наблюдений или оснований. Ключ кэша включает версии, период, политику доступа и конфигурацию модели. Сохранять историю и не плодить повторные версии без изменений.
7. Фидбек «не относится к метрике», «неверный канал», «не хватает контекста» сохранять для оценки качества. Изменение профиля и обучение/публикация конфигурации требуют отдельного контролируемого процесса.
8. Проверки: точность/полнота связей на размеченных кейсах разных отраслей, качество цитат, отсутствие ложных причинных утверждений, отдельные пустые периоды, неоднозначные единицы, устаревшие определения, утечка между компаниями, ограничение бюджета.

## Работа для backend / Symfony Core

Core остаётся владельцем пользователей, прав, определений метрик, подтверждений, фактических наблюдений, заданий и опубликованных результатов. Python возвращает кандидатов. Использовать существующие PostgreSQL и транспорт claim/heartbeat/result.

Предлагаемые сущности:
- metric_definitions и неизменяемые metric_versions; scope по организации/направлению, owner, visibility, archived_at.
- metric_observations: value, unit/currency, period_start/end, observed_at, источник, статус качества, revision. Расчётные формулы через разрешённый набор операций, без исполнения произвольного кода.
- metric_event_links: версии определения/события, цепочка влияния, evidence, статус проверки, опубликованная версия.
- period_summaries: период, режим знания, as_of, coverage, версии входов, status, результат.
- onboarding_progress: user_id, section, tour_version, completed_at; персональный порядок/видимость карточек отдельно от общих определений.

Предлагаемые внешние API (новые контракты, ещё не реализованы):
- GET /api/companies/{id}/dashboard?from=&to=&mode= — обзор, метрики, свежесть, покрытие, статусы.
- GET/POST /api/companies/{id}/metrics — каталог и создание подтверждённой метрики.
- POST /api/companies/{id}/metrics/prepare — предложение определения через Python.
- PATCH /api/companies/{id}/metrics/{metricId} с expected_version — изменение; архивирование сохраняет историю.
- GET /api/companies/{id}/metrics/{metricId}/events?from=&to=&cursor= — доступные связи и объяснения.
- POST /api/companies/{id}/analysis-jobs — асинхронный анализ; GET задания или SSE для статуса/результата.
- POST /api/feedback — metric/event/assessment/version + тип и текст; сохранить действующие обсуждения, добавив metric_id и period в контекст.
- PUT /api/me/onboarding/{section} — прогресс обучения и версия подсказки.

Во всех маршрутах проверять членство и права; Python service token не передавать браузеру. Ограничить пагинацию, стоимость, частоту и размер заданий. Поддержать идемпотентность, отмену, ошибки и частичные результаты. Источник/валюта/период должны быть известны до агрегации; в консолидированных значениях исключать внутригрупповые обороты по согласованной методике.

## Очередность и критерии приёмки

1. Утвердить определения, дизайн карточек и структуру MetricDefinition/MetricImpact.
2. Реализовать хранение, права и API метрик; подключить dashboard к данным без модельных вызовов.
3. Подключить prepare-metric, отбор материалов и доказуемые связи; проверить ручную разметку.
4. Подключить обзор периода, очереди, версии, наблюдения и существующие чаты/фидбек.
5. Проверить: метрика компании A не видна B; смена периода сохраняется в URL/настройках; нет данных отображается явно; каждый вывод открывает основание; все новые версии воспроизводимы; обучение доступно с клавиатуры и повторно по запросу.

## Проверка текущей вёрстки

Сборка и валидатор статического артефакта проходят. Существующие 37 тестов логики проходят. Браузером проверяются вход, обучение, переход метрика → материалы, обсуждение источника, периоды и добавление метрики. Backend/ML в рамках этой итерации не запускались и не изменялись.

## Уточнение UX: единый обязательный тур

На главной применён общий набор: выручка, операционная маржа, денежный поток, долговая нагрузка, срок оплаты клиентами и операционные расходы. Поставки в срок заменены расходами. Отраслевые сведения остаются в материалах и в персональных разборах, а не в определении универсального показателя.

Обучение — последовательность из девяти шагов по реальным экранам. Текст появляется постепенно, помощник увеличен. Продолжить можно после полного показа текста и короткой паузы; это не проверка фактического прочтения. Тур показывается компактной панелью поверх края страницы. Страница остаётся доступной, помощника можно свернуть до небольшой кнопки и развернуть для продолжения. Позиция сохраняется после каждого подтверждения, перезагрузка возобновляет незавершённый шаг. completedAt записывается только в конце. После завершения автоматические модалки выключены во всех разделах; вопрос в шапке запускает добровольный повтор. При reduced motion текст показывается сразу. Сервер должен хранить tour_version, next_step и completed_at по пользователю, а не по компании.
