# Как работает AI/Data-модуль

Python получает от PHP Core задачу с готовыми правами, контекстом бизнеса и снимком источников. Затем он выполняет работу локально и возвращает проверяемого кандидата. PHP решает, принять ли его и показать пользователю.

```text
Core: контекст + разрешения + политика
          ↓ ai-data-task-v1
Python: сбор → документы/evidence → события → общий разбор → компания/период
          ↓ ai-data-result-v1
Core: проверка актуальности → публикация или отказ
```

## Что приходит

`DataTask` содержит tenant/company и request IDs, версии контекста и политики, дату `as_of`, операцию (`collect`, `analyze`, `reassess`, `period`, `onboard`, `optimize`, `rollback_config`, `prepare_description`), snapshot источников, до 20 разрешённых профилей бизнесов, лимит событий, бюджет и классификацию данных.

Core также может приложить список `published_assessments`: точные подписи оценок, которые уже были опубликованы. Это важно: локальный кеш Python не знает, получил ли Core предыдущий ответ.

## Что происходит

1. Python проверяет tenant, версии, lease, даты и бюджет.
2. Collector запрашивает только источники из snapshot. Новую ссылку он не ищет сам и не превращает разовый probe в подписку.
3. Материалы сохраняются версиями с URL, датой, publisher/author при наличии, исходным SHA256 и фрагментами для поиска.
4. Перепечатки объединяются в события и общий пакет доказательств; затем находятся релевантные пути к конкретным зависимостям бизнеса.
5. Исследователь ищет недостающие основания в разрешённом корпусе, аналитик готовит вывод, критик проверяет слабые места. Это этапы одного pipeline; отдельные сервисы или три вызова моделей не обязательны.
6. Проверки сопоставляют цитаты, версии и scope. Если входы не изменились и Core proof приложен, получается `no_change`. Иначе workflow возвращает candidate и причину новой revision. Если отбор не нашёл связи события с компанией, результат остаётся partial с вопросом о зависимости, даже при формально правильном ответе модели.

При `collect` сбор не обещает найти все новости: он проверяет только включённые в snapshot источники. Источники, издатели и типы настраивает Core; персональное скрытие публикации не меняет выдачу анализа. Поиск внутри AI/Data ограничен сохранённым корпусом. Для конкретного бизнеса пути воздействия строятся из переданного графа и evidence, а платежи или совпадение `GROUP_ID` не доказывают цепочку поставок.

Всё исполнение ограничено deadline, lease, параллельностью и общим бюджетом модели. Потеря lease блокирует отправку результата. После отправки Worker сохраняет точный payload до ACK Core.

## Что возвращается

`DataResult` несёт `status`, версии, отчёт collection, события и доказательства, кандидаты по бизнесам, `revisions`, конфигурации аналитика, покрытие и этапы выполнения. Кандидат объясняет возможную цепочку влияния, показывает evidence, альтернативы, неизвестное и условия наблюдения. Неизвестные договоры, запасы и связи не заполняются догадками.

Статусы задачи (`completed`, `partial`, `no_change`, `unknown`) и кандидата (`ready`, `partial`, `unknown`) относятся к разным уровням. `partial` должен сохранять конкретные ограничения в `coverage.limitations` и вопросы в `clarifications`; Core решает, показывать ли кандидата или попросить уточнение. `no_change` требует точного proof уже опубликованной оценки от Core. Нулевой сигнал отбора и `unknown` не доказывают отсутствие риска.

`publication_revision_required` в записи revision — явный сигнал для Core. Candidate не является опубликованной ситуацией. Один `input_signature` не должен получать вторую revision только из-за повторной доставки или нового job ID.

## Где хранятся данные

- PHP Core остаётся источником истины для пользователей, прав, профиля компании, расписания и опубликованных ситуаций.
- Python Intelligence хранит корпус, события, конфигурации, этапы workflow, бюджет и outbox в отдельной PostgreSQL-базе `business_context_ai`; для таблиц применяются component schemas и `store_key`/RLS. `--state-dir` задаёт логические пути/namespaces и private filesystem, а не SQLite базу рабочего сервиса.
- Сырые полученные ответы коллектора лежат отдельно в private `raw/tenants/<tenant-hash>/...`; в report/receipt остаются их SHA256 и ссылка.
- Docker Compose хранит сырые оригиналы в volume `alfa-business-context-intelligence-state`, а PostgreSQL — в отдельном `alfa-business-context-postgres`. Хостовый процесс и контейнер используют одну БД только если им заданы одинаковые DSN и storage namespace.

Это отдельное хранилище AI/Data, а не БД Symfony/Core и не доказательство доступа к банковскому PostgreSQL. Core остаётся владельцем канонического профиля и очереди; PHP интеграция пока не подключена. Реальные банковские PDF/CSV надо предоставить и разрешить отдельно; их ещё не проверяли. Старую SQLite можно импортировать только контролируемой read-only командой, описанной в [руководстве PostgreSQL](postgresql.md).

Обезличенный CSV может быть чисто преобразован через `/internal/v1/company-context/prepare` в `CompanyContextProposal`; Core отдельно проверяет и сохраняет факты. Описание компании обрабатывается `prepare_description`: детерминированно в CLI `prepare-description` или HTTP `POST /internal/v1/company-context/from-description`, а при явно выбранном DataTask `operation=prepare_description` — также разрешённым LLM-маршрутом. Во всех вариантах возвращается предложение, канонический профиль Core не обновляется. Обычный DataTask сохраняет proposal в workflow result cache. Внешний вызов запрещён для `confidential`; Core принимает предложение и сохраняет собственную версию профиля. Величина `REVENUE_COMPANY` не даёт определить единицу автоматически. Если единица не подтверждена, право пройти пороговую маршрутизацию остаётся неизвестным. Поля клиента не передаются внешней модели при преобразовании CSV.

## Профиль, baseline и продолжение оптимизации

`onboard` сразу создаёт базовую конфигурацию с версией и fingerprint полученного профиля; обычный анализ может использовать её сразу. Базовый персональный отбор зависит от подтверждённых сведений и зависимостей, а не от отраслевой ветки. Лексический сигнал помогает поставить событие в очередь, но не доказывает причинность, размер эффекта или финансовую тяжесть.

После успешного создания/пересборки конфигурации Python может приложить в `DataResult.follow_up_intents` типизированный `optimize_company_analyst` intent с fingerprint профиля, ожидаемой ревизией и idempotency key. Core проверяет intent и принятый результат, затем применяет отдельную `AutoOptimizationPolicy` с собственными конечными лимитами и явным резервом. При отсутствии разрешённой allocation автоматическая оптимизация получает `skipped_budget`; бездействие не трактуется как ошибка профиля. При разрешении Core ставит обычную задачу `operation=optimize`, а не отдельный pipeline или турнир.

PHP hook на сохранение компании и пользовательское приложение пока не подключены; автоматизация проверяется на fixture stand. Подробно: [персонализация профиля и результата](personalization.md).

## Роли и турнир — не одно и то же

Исследователь, аналитик и критик — логические роли внутри одного анализа. Они помогают задать шаги поиска и проверки, но общий контекст, corpus scope, deadline и бюджет остаются одними.

Турнир — отдельный эксперимент над конфигурациями аналитика. Baseline и несколько конкурентов проходят одинаковые train cases; после программных проверок сравниваются вслепую, затем финалист проверяется на отложенных и свежих shadow примерах. Человек оценивает слепой пакет. Только пригодный несинтетический отчёт с holdout/shadow и reviewer может быть продвинут; rollback создаёт новую версию прежней конфигурации. Маленький учебный турнир подтверждает механику, но не доказывает улучшение качества.

Не следует подменять этот эксперимент самообучением или обещанием персональной точности. Learned ranking и embeddings не включены как production-компоненты; они требуют отдельного согласования модели, входных данных и проверки. Независимая ручная разметка 200–300 реальных кейсов пока не выполнена.

Подробные команды: [интеграция backend/frontend](ai-integration.md), [персонализация](personalization.md), [турнир](../apps/intelligence/docs/tournament.md), [настройки аналитика](../apps/intelligence/docs/analysts.md). Полный локальный пример запускается командой `python -m intelligence demo-data` из `apps/intelligence`; он использует только синтетические файлы репозитория и offline fixture transport.


## Профиль смешанного бизнеса

`company-context-v2` сохраняет все направления в `activities`. Например, производство датчиков, разработка ПО и импорт компонентов — три направления одной компании. Нормализованный класс может быть неизвестен; это не превращает деятельность в услуги. ОКВЭД остаётся исходным признаком.

В `assertions` передаются продукты, услуги, ресурсы, затраты, рынки, территории, поставщики, группы клиентов, ограничения договоров и горизонты. У каждого пункта есть ID, происхождение, статус и, если известны, даты наблюдения и действия. Система различает `confirmed`, `assumption`, `contradiction`, `unknown`. Старые `facts` и `dependencies` принимаются. Запись без дат не получает выдуманную актуальность: результат содержит ограничение и уточняющий вопрос.

Для анализа строится проекция на `as_of`. Будущие наблюдения, просроченные сведения и предположения не становятся подтверждёнными основаниями. Роль, стиль и горизонт пользователя передаются отдельно в `businesses[].preferences`; они не меняют факты, права и требования к доказательствам.

## Как выбирается и меняется аналитик

1. `onboard` сразу создаёт рабочую базовую конфигурацию без обращения к модели.
2. Core может поставить отдельную задачу `optimize`, указав `expected_config_revisions` для каждой компании. Генератор получает ограниченные признаки и выбирает поля стратегии. Лимиты модели общие с заданием; ошибка оставляет прежние настройки.
3. Следующий анализ применяет сохранённую конфигурацию к поиску, исследованию, основному ответу и критике. Фактическая версия записывается в `candidate.versions.analyst_config`; поисковые запросы и этапы видны в `trace`.
4. При изменении профиля создаётся новая версия настройки. Старое задание не может заменить результат нового профиля. `rollback_config` восстанавливает прежнюю стабильную стратегию новой ревизией, сохраняя текущий профиль.

Ограниченная генерация предпочтений не означает победу в турнире. Турнир сравнивает baseline и до трёх кандидатов отдельно от обработки новостей. Его публикация требует свежих holdout/shadow, слепой проверки и пройденных обязательных условий. [Настройки](../apps/intelligence/docs/analysts.md), [турнир и команды](../apps/intelligence/docs/tournament.md).

## Обновление и период

Сначала события ранжируются по подтверждённым направлениям и зависимостям. Перед ограничением `max_events` предусмотрен ограниченный просмотр события с нулевым сигналом; в расписании `max_exploratory_analyses` допускает до трёх углублений в прежнем общем бюджете, по умолчанию одно. Это снижает риск слепого отраслевого фильтра, но не доказывает полноту отбора.

Событие и компания образуют стабильную пару. Ручной пересчёт возвращает новую оценку этой пары; Core устраняет повтор публикации по `input_signature`. Изменение источников, профиля, активной проекции, конфигурации или режима анализа меняет подпись входа. Исключённый источник проверяется до получения материалов из корпуса и повторного использования кандидата.

`period` возвращает показатели, хронологию и персональные кандидаты по событиям выбранного периода. `as_known` использует меньшую из `as_of` и конца периода и проверяет серверное получение материалов. Для недатированного профиля нужен исторический Core-снимок `businesses[].known_at` не позже этой границы; иначе берутся только записи с `observed_at`, а недатированный граф исключается; `retrospective` явно использует сегодняшнее знание. Историческое исследование не заменяет текущий мониторинговый результат и не откатывает текущую конфигурацию компании. Оно не доказывает причинность изменений показателей.

## Проверить новый пример

Из корня репозитория:

```sh
docker compose run --build --rm intelligence demo-business
```

Команда читает два локальных RSS, проходит сбор → корпус → два события → две компании → четыре кандидата. Первая компания производит датчики, пишет ПО и импортирует керамические компоненты; вторая занимается ПО. Сообщение о задержке и контрсообщение объединены в одну группу с двумя источниками; слабая аналогия остаётся отдельным событием. Сеть источников и модели по умолчанию не используются. Результат честно остаётся ограниченным baseline.

[Входной пример](../apps/intelligence/examples/business-scenario.json) содержит полноценный DataTask. Сам `run-task` с `operation=analyze` требует заполненного корпуса; `demo-business` дополнительно подаёт RSS из `examples/feeds`. [Ожидаемые основания и запрещённые выводы](../apps/intelligence/evaluation/business-scenario.json) отделяют функциональную проверку от оценки качества настоящей модели.

Исторические события сохраняются в отдельном артефакте `historical-events/`; его namespace записывается в `coverage.event_snapshot_ref` и `versions.event_snapshot`. Это не вторая очередь и не владелец профиля: исторический разбор не меняет текущий EventStore. Повторное получение старого `document_revision_ref` также не становится новой текущей версией публикации.

Неподтверждённые текущие зависимости участвуют в ограниченном поиске и вопросах отдельно от подтверждённых оснований. Исследователь и критик могут искать дополнительные сведения только в разрешённом корпусе. `usage.search_coverage` и ограничения объясняют границы поиска; ненайденная связь не равна отсутствию риска. [Косвенные примеры и реальный турнир](research-and-tournament-checks.md), [подключение Symfony](symfony-integration.md).
