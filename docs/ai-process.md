# Как работает AI/Data-модуль

Python получает от PHP Core задачу с готовыми правами, контекстом бизнеса и снимком источников. Затем он выполняет работу локально и возвращает проверяемого кандидата. PHP решает, принять ли его и показать пользователю.

```text
Core: контекст + разрешения + политика
          ↓ ai-data-task-v1
Python: сбор → документы/evidence → события → общий разбор → компания/период
          ↓ ai-data-result-v1
Core: проверка актуальности → публикация или отказ
```

## Что приходит

`DataTask` содержит tenant/company и request IDs, версии контекста и политики, дату `as_of`, операцию (`collect`, `analyze`, `reassess`, `period`, `onboard`), snapshot источников, до 20 разрешённых профилей бизнесов, лимит событий, бюджет и классификацию данных.

Core также может приложить список `published_assessments`: точные подписи оценок, которые уже были опубликованы. Это важно: локальный кеш Python не знает, получил ли Core предыдущий ответ.

## Что происходит

1. Python проверяет tenant, версии, lease, даты и бюджет.
2. Collector запрашивает только источники из snapshot. Новую ссылку он не ищет сам и не превращает разовый probe в подписку.
3. Материалы сохраняются версиями с URL, датой, publisher/author при наличии, исходным SHA256 и фрагментами для поиска.
4. Перепечатки объединяются в события и общий пакет доказательств; затем находятся релевантные пути к конкретным зависимостям бизнеса.
5. Исследователь ищет недостающие основания в разрешённом корпусе, аналитик готовит вывод, критик проверяет слабые места. Это этапы одного pipeline; отдельные сервисы или три вызова моделей не обязательны.
6. Проверки сопоставляют цитаты, версии и scope. Если входы не изменились и Core proof приложен, получается `no_change`. Иначе workflow возвращает candidate и причину новой revision. Если отбор не нашёл связи события с компанией, результат остаётся partial с вопросом о зависимости, даже при формально правильном ответе модели.

При `collect` сбор не обещает найти все новости: он проверяет только включённые в snapshot источники. Источники, издатели и типы настраивает Core; персональное скрытие публикации не меняет выдачу анализа. Поиск внутри AI/Data ограничен сохранённым корпусом. Для конкретного бизнеса пути воздействия строятся из переданного графа и evidence, а платежи или совпадение `GROUP_ID` не доказывают цепочку поставок.

Всё исполнение ограничено deadline, lease, параллельностью и общим бюджетом модели. Потеря lease блокирует отправку результата. После отправки Worker сохраняет точный payload до ACK Core.

## Что возвращается

`DataResult` несёт `status`, версии, отчёт collection, события и доказательства, кандидаты по бизнесам, `revisions`, конфигурации аналитика, покрытие и этапы выполнения. Кандидат объясняет возможную цепочку влияния, показывает evidence, альтернативы, неизвестное и условия наблюдения. Неизвестные договоры, запасы и связи не заполняются догадками.

`publication_revision_required` в записи revision — явный сигнал для Core. Candidate не является опубликованной ситуацией. Один `input_signature` не должен получать вторую revision только из-за повторной доставки или нового job ID.

## Где хранятся данные

- PHP Core остаётся источником истины для пользователей, прав, профиля компании, расписания и опубликованных ситуаций.
- Python хранит локальную SQLite-копию корпуса, события, конфигурации, этапы workflow, бюджет и outbox в `--state-dir` (по умолчанию `apps/intelligence/.state`).
- Сырые полученные ответы коллектора лежат отдельно в private `raw/tenants/<tenant-hash>/...`; в report/receipt остаются их SHA256 и ссылка.
- Docker Compose использует named volume `alfa-business-context-intelligence-state`; данные с хоста и контейнера не смешиваются автоматически.

На текущем срезе это локальное durable-хранилище AI/Data, а не общий банковский PostgreSQL. Реальные банковские PDF/CSV надо предоставить и разрешить отдельно; их ещё не проверяли.

Обезличенный CSV может быть чисто преобразован через `/internal/v1/company-context/prepare` в `CompanyContextProposal`; Core отдельно проверяет и сохраняет факты. Величина `REVENUE_COMPANY` не даёт определить единицу автоматически. Если единица не подтверждена, право пройти пороговую маршрутизацию остаётся неизвестным. Поля клиента не передаются внешней модели при таком преобразовании.

## Роли и турнир — не одно и то же

Исследователь, аналитик и критик — логические роли внутри одного анализа. Они помогают задать шаги поиска и проверки, но общий контекст, corpus scope, deadline и бюджет остаются одними.

Турнир — отдельный эксперимент над конфигурациями аналитика. Baseline и несколько конкурентов проходят одинаковые train cases; после программных проверок сравниваются вслепую, затем финалист проверяется на отложенных и свежих shadow примерах. Человек оценивает слепой пакет. Только пригодный несинтетический отчёт с holdout/shadow и reviewer может быть продвинут; rollback создаёт новую версию прежней конфигурации. Маленький учебный турнир подтверждает механику, но не доказывает улучшение качества.

Не следует подменять этот эксперимент самообучением или обещанием персональной точности. Learned ranking и embeddings не включены как production-компоненты; они требуют отдельного согласования модели, входных данных и проверки. Независимая ручная разметка 200–300 реальных кейсов пока не выполнена.

Подробные команды: [интеграция backend/frontend](ai-integration.md), [турнир](../apps/intelligence/docs/tournament.md), [настройки аналитика](../apps/intelligence/docs/analysts.md). Полный локальный пример запускается командой `python -m intelligence demo-data` из `apps/intelligence`; он использует только синтетические файлы репозитория и offline fixture transport.
