# Требования и границы решения

## Как читать этот документ

- **Обязательно по кейсу** — требование из брифа хакатона; его невыполнение угрожает соответствию решения или оценке.
- **Предложение продукта** — целевое поведение и архитектура из продуктового PDF. Это не автоматически требование хакатона и не доказательство доступности систем Альфы.
- **Проверено** — бриф прочитан целиком (19 страниц), продуктовый PDF v2 (44 страницы) и новая редакция v3 (52 страницы) прочитаны/сопоставлены по извлечённому тексту. Проверено наличие и формулировки требований в этих источниках.
- **Неизвестно / не проверено** — доступ к production-системам, разрешённым источникам и их лицензиям не подтверждён. Закрытые CSV и PDF организаторов теперь предоставлены и проверены локально; их состав, ограничения и фактический импорт описаны ниже и в [инструкции кейса](judging.md). Актуальные проверки моделей приведены в [отчёте](ai-live-checks.md). Утверждения продуктового PDF об аудите версии 10.0.0 — заявления этого документа, не независимая проверка текущего репозитория.

Текущий локальный срез состоит из React/nginx, Symfony Core/PHP и Python Intelligence; web обращается к Core, Core выполняет прямой baseline news-вызов Python. Это не означает, что реализованы общая Core job queue/worker lifecycle, банковский SSO или production эксплуатация. Статус текущей интеграции: [проверка 26 октября](product-docker-checks.md); фактические границы — [архитектура](architecture.md) и [формат Python](../contracts/intelligence/README.md).

### Что изменилось в v3 относительно v2

- v2 предлагал Node BFF + Java/Spring Core; v3 заменяет целевой Core на PHP 8.4/Symfony 7.4 modular monolith и говорит, что отдельный собственный Node backend не обязателен (v3, с. 1, 11–19; переход виден в diff к v2).
- Python остаётся отдельным AI/Data сервисом; уточнены claim/lease/result API, разделение DB-ролей/схем, отсутствие прямой записи Python в бизнес-таблицы и отдельные пулы worker-ов (v3, с. 12, 16, 19).
- Необязательность Kafka сохраняется; v3 уточняет разграничение Messenger для коротких PHP-задач и Core API/lease для Python jobs. SSE hub вынесен в отдельный канал; Redis/Qdrant зависят от контракта/потребности (v3, с. 11, 15–19, 31).
- Продуктовая концепция, разрешённые модели, бюджет 500 ₽/день и качество анализа не заменены. Целевой продуктовый документ расширен до 52 страниц, включая Symfony-specific детали и новые задачи backend (v3, с. 31–52).

## Ключевые риски и несовпадения документов

1. **Фокус.** Бриф — ЛПР крупного бизнеса с выручкой свыше 15 млрд руб.; продуктовый PDF расширяет адресата до любого бизнеса Альфа-Бизнеса. Для сдачи приоритет — крупная компания и роли ЛПР; широкий рынок — направление развития.
2. **Агентность.** Однократная генерация и готовый сторонний агент запрещены. Требуется собственная многошаговая логика с инструментами, контекстом, проверкой и адаптацией; число агентов не оценивается само по себе.
3. **Модели и цена.** Разрешены только модели из брифа; названия в PDF нельзя считать API model_id. Лимит 500 ₽ относится к общему ключу команды; локальный счётчик не гарантирует соблюдение общего лимита, если есть вызовы вне общего broker.
4. **Данные и доказательства.** Данные организаторов импортированы в локальную judging-среду и остаются синтетическими/обезличенными. Единицы выручки неизвестны, конфликтный ID исключён из профилей, а платежи и отсутствующие ссылки требуют осторожной интерпретации. OCR-цитаты сверяются с оригиналами.
5. **Интеграции.** Предложения AlfaGen/банковского RAG, Kafka, Qdrant, SSO и production shell не являются предоставленным доступом. Продуктовый PDF сам требует сверки с владельцами платформ.
