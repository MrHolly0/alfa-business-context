# Структура данных Backend по кейсу «Новостная аналитика»

Источник: «Альфа Хак_Новостная аналитика (1).pdf», стр. 4–7, 9–10, 13–17. Это проект схемы по описанию полей. Фактические CSV/PDF не включены в репозиторий; до миграции нужны заголовки, типы, пропуски, единицы и реальные размеры файлов.

## 1. Исходные данные кейса

### `company_imports` — одна строка юридического лица из `df_Uid_data_hack.csv`

Ключ: `(dataset_version, synthetic_u)`. Обязательные технические поля: `import_id`, `dataset_version`, `source_file`, `source_row`, `imported_at`, `raw_json`, `raw_hash`. Это защищает исходник от потери и позволяет повторно проверить любой вывод.

| Поле PDF | Хранение | Комментарий |
|---|---|---|
| `SYNTHETIC_U` | text, not null | Псевдоним компании только внутри версии набора |
| `ORG_TYPE`, `OKFS_NAME`, `COMPANY_AGE_YEARS_GRADATION`, `ECO_MARK_LABEL` | nullable text | Категориальные значения как в CSV |
| `MAINOKVED_CODE`, `MAINOKVED_NAME` | nullable text | Код хранить строкой, не числом |
| `NEGATIVEMARK` | nullable text | Сохранить исходный код; смысл проверить по словарю CSV |
| `AMOUNT_WORKERS_FNS_GRADATION`, `AMOUNT_WORKERS_SPARK_GRADATION` | nullable text | Диапазоны, не точное число работников |
| `CL_TYPE` | nullable text | Клиент или потенциальный клиент |
| `CL_PRODUCT_RKO_MARK`, `CL_PRODUCT_GAR_MARK`, `CL_PRODUCT_LOA_MARK`, `CL_PRODUCT_LEA_MARK`, `CL_PRODUCT_DEP_MARK`, `CL_PRODUCT_ZPP_MARK` | nullable text | Исходные значения флагов; нормализованные boolean nullable отдельно |
| `FTS_FLAG`, `FTS_COUNTRY_NAME` | nullable text | Наличие информации и страна по данным ФТС; страна не доказывает текущую поставку |
| `FACTORING_MARK` | nullable text | Исходное значение флага |
| `REVENUE_COMPANY` | raw text + nullable numeric | PDF называет годовой выручкой; единицу и год нужно подтвердить до сравнения с порогом 15 млрд ₽ |
| `GROUP_ID` | nullable text | Идентификатор группы, не доказательство контрагентской связи |
| `CITY`, `REGION` | nullable text | Регистрация, не обязательно фактический рынок присутствия |

В приложении 1 ровно 24 поля юридического лица. Значения `0.0`, пустая строка и отсутствие колонки имеют разный смысл; нормализация в `false`/`unknown` допускается только по проверенному словарю.

### `person_company_links` — `df_Fid_Uid_link_hack.csv`

Ключ `(dataset_version, synthetic_f, synthetic_u)`; поля `SYNTHETIC_F`, `CITY_NAME`, `RC_NAME`, `SYNTHETIC_U` плюс `import_id`, номер строки и raw JSON. Связь описывает обезличенного человека и компанию, но не раскрывает должность, полномочия или реальную личность. Не смешивать эти строки с пользователями интернет-банка.

### `payment_aggregates` — строки с `BENEFICIARY`, `PAYER`, `PAY_AMT`, `PAY_CNT`

Ключ загрузки — `import_id + source_row`; не делать уникальность только по паре компаний, пока не известны период и разрез агрегации. `payer_id`, `beneficiary_id` ссылаются на `SYNTHETIC_U` в том же dataset_version. `PAY_AMT` хранить как `amount_raw` и `amount_numeric`, `PAY_CNT` как `count_raw` и `count_numeric`, оба с nullable `unit`, `period_start`, `period_end`, `currency`. Без подтверждённых единиц/периода нельзя строить денежные метрики или динамику. Платёж подтверждает поток денег в агрегате, но сам по себе не доказывает поставку или направление физического товара.

**Замечание к PDF:** на стр. 16 для платежей повторено имя файла `df_Fid_Uid_link_hack.csv`, указанное и для физических лиц. Перед импортом нужно сверить фактическое имя и заголовки файла; нельзя приписывать платёжные поля этому CSV без проверки.

## 2. Бизнес-контекст и доступ

- `users` — пользователь банковского интерфейса; ID и роль из защищённой сессии, не из `SYNTHETIC_F`.
- `company_memberships` — `user_id`, `company_id`, scope/role, статус и период действия. Каждое чтение/изменение требует проверки членства и права.
- `company_context_versions` — версия подтверждённого контекста с `company_id`, временем, автором, источником, JSON фактов, статусом подтверждения. Исходная CSV-строка не перезаписывается.
- `business_activities`, `company_geographies`, `counterparty_hypotheses` — расширенные направления, регионы, возможные связи и уровень подтверждения. `GROUP_ID` и платежи могут предложить гипотезу, но не превращаются автоматически в факт поставки.
- `metric_definitions`/`metric_versions` — название, смысл, единица, формула, scope компании/направления, частота, источник данных, видимость и пороги. Новую пользовательскую метрику можно описать текстом, затем подтвердить машинное предложение.
- `metric_observations` — числовое значение, период, валюта, источник, качество/подтверждение, версия. Если значения нет, API возвращает `status: no_data`, а не ноль.
- `onboarding_progress` — `user_id`, `tour_version`, `next_step`, `completed_at`; хранить по человеку, не по компании.

PDF даёт только ограниченные признаки клиента. Он не содержит баланс счетов, маржу, денежный поток, DSO, EBITDA, остатки сырья или фактические значения универсальных карточек. Для них нужны отдельные банковские/учётные источники либо ручное подтверждённое заполнение. Пока API отдаёт `no_data` и демонстрационные данные маркируются отдельно.

## 3. Новости и анализ

- `source_policies`: разрешённые источники, включение/исключение, scope компании, версии политики и сроки.
- `documents`: первоисточник, URL/файл, автор, дата публикации, дата события, вид материала (`external`, `bank_analytics`, `user_input`), тип высказывания, сырой hash, версия и доступ.
- `document_chunks`/`claims`: точные фрагменты и утверждения с типом `observed_fact`, `opinion`, `forecast`, `hypothesis`; ссылка на оригинал и страницу/позицию. Девять названий банковских материалов из приложения 2 — каталог ожидаемых источников, не доказательство, что все тексты загружены.
- `events`: нормализованное событие и версии; `event_documents` связывает перепечатки и независимые источники.
- `analysis_jobs`: компания/группа, версии контекста и политики, период, состояние, бюджет, deadline, lease, idempotency key. Python получает разрешённый снимок и возвращает кандидата.
- `assessment_candidates`: возможное влияние, механизм, риск/возможность, горизонт, альтернативы, неизвестное, уточняющий вопрос, предложенное действие и статус проверки.
- `assessment_evidence`: ссылки кандидата на версии документа, конкретные фрагменты, признаки компании и позицию банка. Каждое существенное утверждение должно быть трассируемым.
- `published_assessments` и `assessment_revisions`: публикацию решает Core; версия результата не перезаписывает прошлую.
- `metric_event_links`: отдельная подтверждаемая связь события с метрикой и цепочка влияния. Тематическая похожесть не равна количественному изменению значения.
- `feedback`, `discussions`, `work_items`: замечания, вопросы, ответы помощника, ответственные, сроки и статусы, привязанные к версии оценки/метрики и компании.

## 4. Контракт экрана

`GET /api/companies/{id}/dashboard?from=&to=` возвращает метрики с `{value, unit, period, status, provenance}`, сводку событий, покрытия и свежести. `GET /api/companies/{id}/metrics/{metricId}/events` отдаёт карточки с evidence и статусом связи. `POST /api/companies/{id}/metrics/prepare` возвращает предложение определения и вопросы, `POST /metrics` сохраняет подтверждённую версию, `POST /analysis-jobs` запускает асинхронный анализ. Отдельно нужны `GET /analysis-jobs/{id}`, feedback/discussions и onboarding. Пользовательская авторизация остаётся в Core; Python service token браузеру не выдаётся.

## 5. Порядок реализации

1. Получить настоящие файлы и словари. Проверить спорное имя платежного файла, единицы, год выручки, период платежей, кодировку, дубликаты и пропуски. Зафиксировать версию набора и контрольные суммы.
2. Создать Symfony Core, PostgreSQL-миграции, импорт в неизменяемые staging-таблицы и проверку ссылок между компаниями, физлицами и платежами. Не импортировать банковских пользователей из файла физлиц.
3. Добавить сессию/членство/права, версии контекста, подтверждение и аудит изменений. Все API фильтровать по компании и роли.
4. Подключить реальные или ручные наблюдения метрик. Определить формулы и единицы. Возвращать `no_data` там, где кейс не даёт значения; убрать синтетический баланс из ответа production API.
5. Сделать управление источниками и корпусом документов с происхождением, версиями, дедупликацией и правами. Подключить девять банковских материалов после фактической загрузки и разрешения.
6. Связать Core с уже существующим Python worker через версионированное задание и результат. Публиковать только кандидатов с допустимыми основаниями, сохранять историю и идемпотентность.
7. Реализовать API дашборда, метрика → события, сводки периода, обратной связи и прогресса обучения. Подключить текущий frontend к этим API, оставив демо как явный режим.
8. Проверить сквозной сценарий, изоляцию компаний, пересчёт при смене контекста/источника, пустые данные, ошибочные единицы, повтор задания, права, качество связей и трассировку до оригинала.
