# Команда и распределение работ

## Доступная команда

Планирование ведётся на четырёх активных участников. Product/Business Analyst совмещает продуктовую проработку, prompt engineering и рубрику оценки. Frontend, Backend и ML Engineer — отдельные активные роли. Пятый участник временно в отъезде; дедлайн неизвестен, поэтому работа должна оставаться выполнимой четырьмя участниками, без задач, которые ждут только его.

| Роль | Основной результат | Задачи backlog |
|---|---|---|
| Product / BA + Prompt Engineer | Персона и сценарий, продуктовые состояния, JSON Schema вместе с ML, промпты, rubric, размеченные примеры, оценка полезности и риска ошибок | R-01, R-07 (совместно), R-12 (с Backend/ML), R-14–R-18, приёмка R-10/R-15 |
| Frontend | Интерактивный путь, карточки, источники, состояния загрузки/ошибок, адаптация под доступные API-контракты | R-10, часть R-11, R-13 (документация запуска UI), R-17/R-23 позднее |
| Backend | Текущий прототипный Node API остаётся reference; целевая зона — Symfony Core, PostgreSQL jobs/outbox и контракт с Python. Конфигурация, права и граница вызовов | R-05, R-11–R-13, R-21, R-25–R-27; пилотное hardening — R-22 |
| ML Engineer | Python/FastAPI intelligence, ingest и поиск, ранжирование, агентный pipeline, модели/usage и воспроизводимая оценка вместе с Product/Prompt | R-04–R-09, R-14–R-16, R-18/R-19, R-26/R-27 |
| Участник в отъезде | Не назначается как blocker до подтверждения доступности | Может взять изолированную задачу после возвращения и краткого ревью контекста |

## Порядок и совместная работа

1. Product/Prompt фиксирует сценарий и схему результата. Frontend может независимо собрать экран на согласованном mock JSON.
2. Backend и ML Engineer параллельно закрепляют целевой Symfony Core↔Python HTTP/job контракт; Backend владеет job state в Core, ML — содержимым анализа и Python workers. Прототипный Node runtime не считать уже перенесённым. Один writer на каждый файл.
3. ML делает ingest, evidence retrieval и персональный разбор; Product/Prompt размечает примеры и проводит качественную проверку. Ранний baseline должен появиться до расширения поиска/агентного цикла.
4. Frontend подключается к готовому контракту; вся команда проводит один демонстрационный вертикальный сценарий, затем отдельно проверяет чистый запуск и отчёт качества.

Участник, который не владеет модулем, может ревьюить контракт, критерии и результат. Не создавайте параллельные версии одной схемы или README; назначайте единственного автора документа на время редактирования.
