# ADR-001: целевой бизнес-Core на Symfony/PHP

- Статус: принято как целевое архитектурное направление команды; не реализовано и не подтверждено банком.
- Дата: 2026-10-23.
- Источник: `business-context-product-stack-3.pdf`, 52 страницы; предыдущая редакция продуктового документа — 44 страницы. Сравнение ниже указывает номера страниц новой редакции.

## Решение

Целевое предложение для следующего MVP-среза: React/Core UI обращается к Symfony 7.4 LTS / PHP 8.4 modular Core; отдельный Python AI/Data service выполняет ingest, поиск и анализ. Symfony владеет пользовательскими командами, доступом, jobs, опубликованными оценками и аудитом. Python получает работу через версионированный claim/lease API и передаёт результат как кандидат; он не пишет напрямую в бизнес-таблицы Core. PostgreSQL jobs/outbox и лексический поиск составляют минимальную основу; короткие PHP-задачи могут использовать Messenger. SSE идёт через Mercure или подтверждённый канал банка. Kafka остаётся необязательной, как и в v2; Redis и Qdrant подключаются только по контракту и измеренной необходимости.

## Причина и изменение относительно v2

Редакция v2 предлагала Node BFF + Java/Spring API/Core; редакция v3 предлагает Symfony/PHP Core, а отдельный собственный Node backend считает необязательным. Она уточняет границы двух независимо развёртываемых приложений (Symfony Core и Python AI/Data), JSON API для claim/result, изоляцию схем/ролей PostgreSQL, PHP Messenger для коротких задач и отдельный SSE hub (v3, с. 1, 11–19). Хакатонный стенд v3 также назван как React/Core + Symfony API/CLI workers + Python/FastAPI + PostgreSQL jobs + lexical search (с. 31). Продуктовая логика, агентный анализ, перечень разрешённых моделей и бюджет кейса остаются прежними.

Symfony выбран как актуальное проектное направление из v3, а не как требование кейса или внутренний стандарт Альфа-Банка. В документе прямо оставлены открытыми допуск PHP, образы/расширения, SSO, оболочка, CI/CD, S3/PG и SSE hub (v3, с. 1, 15, 19, 48, 52). Банковский Java стек сам по себе не подтверждает допуск PHP.

## Границы реализации

На 24 октября 2026 веб работает как статический React/nginx; Node используется только для сборки и тестов. Python AI/Data реализован отдельным приложением. Symfony Core пока отсутствует; обмен заданиями проверяется с контрактным стендом. Это частичная реализация принятой архитектуры, без подтверждения банковской интеграции.

Для кейсового MVP команда может выделить минимальный Core job/outbox + Python claim/result путь и базовую изоляцию данных. Не переносить все v3 задачи с меткой P0 в хакатонный scope: в PDF P0 относится к этапу «до пилота». Если в MVP реализован lease, обязательны идемпотентность и отбрасывание stale lease/result; расширенные retry/failure transport, recovery, HA, load/SLO, немедленный отзыв SSE и production security review относятся к пилотным воротам и зависят от ресурсов/решений владельцев платформы.

## Последствия и открытые вопросы

- Backend владеет Symfony Core, миграциями, jobs и REST-контрактами; ML владеет Python workers и AI/Data; оба согласуют claim/heartbeat/result. Product/BA + Prompt задаёт сценарий, рубрику и контракт результата; Frontend продолжает работу по UI и текущему runtime.
- Нужны composer lock/BOM, проверка совместимости PHP 8.4/Symfony 7.4 и локальный контейнер для нового Core; текущий веб-контейнер не доказывает их наличие.
- До пилота получить ответ банка по PHP-образу и расширениям, SSO, gateway/shell, БД/объектному хранилищу, SSE hub, CI/CD, эксплуатационному владельцу и security требованиям.
- Банковский корпус и API не подключены. Model IDs закреплены в allowlist; metadata шлюза доступны, но тарифы генерации не подтверждены. Текущий статус — в [отчёте проверок](../ai-live-checks.md).
- Не утверждать, что миграция или пилотный дизайн уже работает. Текущее состояние runtime фиксируется отдельно в `docs/demo.md` и `docs/web-status.md`.
